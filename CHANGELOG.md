# Venafi Collection for Ansible

## Version History

##### 1.4.0
* Bumped the `vcert` dependency to `vcert>=0.22.1` in `requirements.in` and regenerated the hash-pinned `requirements.txt` lockfile (`vcert==0.22.1`). `vcert` 0.22.1 delivers, with no collection code change: NGTS (Strata Cloud Manager) service-generated CSR (`csr_origin: service`) enrollment on CIT-only zones — previously failed with `Invalid Zone [...]. The zone format is incorrect` [VC-59232]; working `test_mode: true` enrollment (a duplicate `read_zone_conf` in the fake connector previously raised `NotImplementedError`); tolerance of issuing templates that advertise unrepresentable key sizes/curves during `read_zone`; correct EC-curve casing so service-generated CSRs against curve-constrained templates no longer fail policy validation; and real Ed25519 key generation (an existing Ed25519 key no longer crashes key-type detection).
* Fixed VC-59232 default local-CSR enrollment in `venafi_certificate`: a local CSR with no explicit `privatekey_type` now writes the generated private key to disk. Previously the key file was left unwritten, so the run failed validation with `Private key file does not contain a valid private key`. Also stopped duplicating the failure text when the module's `check()` and `validate()` both ran.
* Fixed `venafi_certificate` ECDSA idempotency: an already-correct ECDSA certificate was re-enrolled on every run because the requested curve (e.g. `P256`) was compared case-sensitively against the SDK's normalized value (`p256`). Curve comparison is now case- and format-insensitive.
* Hardened `venafi_certificate` key parameters: an invalid `privatekey_type`, `privatekey_curve`, or `privatekey_size` now fails with a clear message before any request is made, instead of a raw Python traceback. `privatekey_size` declares `choices`; `privatekey_type` and `privatekey_curve` are matched case-insensitively, with the same aliases as the vcert Go SDK key-type parser (`RSA` / `ECDSA`, with `EC` and `ECC` accepted as `ECDSA`; `P256` / `P384` / `P521` / `ed25519`, with e.g. `p256`, `P-256`, and `ED25519` accepted), so the lowercase spellings that worked in 1.3.1 (e.g. `privatekey_type: EC`, `privatekey_curve: p256`) keep working and stay idempotent whatever casing is used; the module returns the canonical spelling. `privatekey_type: ECDSA` without a curve, or `RSA` without a size, now fall back to the documented defaults (`P521` / `2048`) instead of crashing.
* Fixed the `certificate` role ignoring `certificate_privatekey_curve` with `certificate_remote_execution: true`: the remote path did not forward the curve, so an ECDSA or Ed25519 request silently produced a P-521 key (1.3.1 crashed on the same input). The role README now documents the real curve default (`P521`) and the accepted values.
* Added Ed25519 support to `venafi_certificate`: set `privatekey_type: ECDSA` and `privatekey_curve: ed25519` (requires `vcert>=0.22.1`).
* Fixed the `policy` role silently dropping NGTS credentials: the role now forwards `client_id`, `client_secret`, `token_url`, `tsg_id`, and `scope` to `venafi_policy`, so NGTS policy management works through the role (previously it failed with `Bad credentials list`).
* Updated deprecated imports from `ansible.module_utils._text` to `ansible.module_utils.common.text.converters` in all modules (the `_text` alias is removed in ansible-core 2.24).
* Excluded developer files (`.claude`, `.github`, `.DS_Store`, `.pytest_cache`, `CLAUDE.md`) from the built collection artifact.
* Fixed the `make install` target, which installed a hardcoded `1.0.1` tarball regardless of the collection version.
* Made the `venafi_policy` module idempotent for `state: present`: it now compares the local policy specification against the platform's and only updates when they differ, instead of re-applying (`changed=True`) on every run. The change-detection routine (`policy_utils.check_policy_specification`) was repaired — it previously crashed or reported false differences: elliptic-curve and key-type comparisons are now case-insensitive, list comparisons use exact multiset equality, and NGTS owners/users/approvers (always empty on that platform) are skipped (parity with the Go connector). `state: absent` no longer requires `policy_spec_path` and reports its unsupported-deletion consistently between check mode and apply. Added `venafi_policy` usage examples for Self-Hosted, SaaS, and NGTS. Verified live against Strata Cloud Manager (NGTS) issuing templates.
* `venafi_policy` idempotency also holds for minimal/declarative policy files: any field, list, or nested block the local file omits is treated as "unspecified" and skipped, instead of reporting `changed` on every run (`certificateAuthority` on SaaS and NGTS is the deliberate exception — see the next entry; for Self-Hosted see the TPP `certificateAuthority` entry below). Previously a realistic minimal file (e.g. only `domains` and `keyTypes`, or omitting `maxValidDays` / `ellipticCurves` / the `subject` / `keyPair` / `defaults` blocks) churned forever against a fully-populated platform policy, because omitted scalars and empty lists were compared against the platform's real values. `force: true` remains the escape hatch to re-apply regardless.
* On SaaS and NGTS, `venafi_policy` compares `certificateAuthority` as the **effective** CA that will be applied. The SDK defaults an omitted CA to the built-in default and sends it, so — matching the vcert Go SDK and `terraform-provider-venafi` declarative model (`BuildCloudCitRequest`) — an omitted or explicitly built-in CA that would reset a real remote CA (e.g. DigiCert → built-in) is now reported as a change and shown in check mode, instead of being silently skipped; it converges after one apply. To keep a non-built-in CA on an existing CIT, set `certificateAuthority` explicitly in the policy file. Live-verified against Strata Cloud Manager (NGTS) DigiCert / ZTPKI / built-in CITs. Self-Hosted (TPP) behaves differently; see the TPP `certificateAuthority` entry below.
* `venafi_policy` now detects drift in `subjectAltNames.uriProtocols` and `subjectAltNames.ipConstraints`. Changing the allowed URI protocols or IP constraints while the corresponding `*_allowed` flag stayed the same was silently missed (`changed=False`), so the update was never applied. URI protocols are matched case-insensitively; both are compared only when the local file declares them (an omitted list does not report a false change).
* `venafi_policy` no longer masks connection/authentication failures as "policy does not exist". A failure while reading the current policy (e.g. a mistyped NGTS `token_url`, bad credentials, or a server error) was swallowed and reported as `Creating policy <zone>` (`changed=True`), hiding the real error and defeating idempotency in check mode. Connection, authentication, and unexpected-server errors now fail the task with `Failed to read policy <zone>: <error>`; this includes an unreachable or non-resolving `url`/`token_url` and a `token_url` that answers with a non-JSON page, which previously aborted with a raw `MODULE FAILURE` traceback. Only a genuine not-found still means the policy will be created. On SaaS, the platform's not-found answer for a missing Application or issuing template (an HTTP error whose JSON body carries error code 20215, 20216 or 10051) is recognised, so creating a new SaaS policy (module, check mode, and the `policy` role) and `state: absent` on a missing SaaS zone work.
* `venafi_policy` with `test_mode: true` now fails fast with a clear message instead of aborting with a raw `NotImplementedError` traceback (the fake backend implements no policy operations).
* Stopped emitting the "user/password authentication is deprecated" warning on every SaaS/Self-Hosted run that uses only a token or access token. The warning now fires only when `user` or `password` is actually supplied.
* Fixed `venafi_policy` crashing with `KeyError: 'policy_spec_path'` on `state: absent` when `policy_spec_path` was omitted (the documented, now-supported usage), and ignoring a policy file passed as the canonical `path` option (it failed with `policy_spec_path field not defined`, or `KeyError` in 1.3.1). The module now reads the canonical `path` value, which Ansible fills for both `path` and the `policy_spec_path` alias and expands (`~`, `$VAR`); a `~/...` file path previously failed with `File at ~/... does not exist`.
* Fixed `venafi_policy` idempotency drift-detection crashing with `TypeError: 'NoneType' object is not iterable` when the platform returns no value for a list field the policy file declares (e.g. `subjectAltNames.uriProtocols`/`ipConstraints`/`domains` against a CIT that does not constrain them). The drift is now reported instead of raising.
* Fixed `venafi_policy` `certificateAuthority` idempotency on CyberArk Certificate Manager, Self-Hosted (TPP). The effective-CA comparison (which defaults an omitted CA to the built-in `DEFAULT_CA`) is a SaaS/NGTS concept; on TPP a folder that locks no CA reads back empty, so the module reported `changed=True` on every run and apply pushed a SaaS CA string into the folder. TPP now diffs `certificateAuthority` only when the file sets a real, non-default CA, and apply no longer writes the SaaS built-in CA (`BUILTIN\Built-In CA\Default Product`, the SDK default for an omitted CA) into the folder: an omitted or built-in CA is left unset so the folder inherits its parent's CA (as the vcert Go connector does for an omitted CA). To pin a CA on a Self-Hosted folder, set `certificateAuthority` explicitly in the policy file (SaaS/NGTS behavior unchanged).
* Fixed `venafi_policy` idempotency missing a `keyPair.serviceGenerated` change, which could leave a CSR-generation restriction unenforced. On SaaS and NGTS an issuing template that allows both CSR upload and service-generated keys reads back with no `serviceGenerated` value, and the comparison treated that as `false`: a local `serviceGenerated: false` (CSR upload only) went undetected, so when nothing else in the policy file differed the module reported `No changes detected`, never applied it, and the template kept accepting service-generated keys (1.3.1 re-applied on every run and did enforce it). `serviceGenerated` is now compared as three states on SaaS/NGTS (`true`, `false`, or both allowed) and converges after one apply. On Self-Hosted (TPP) an explicit `serviceGenerated: false` (in `policy.keyPair` or `defaults.keyPair`) is now reported as a change when the folder still reports service-generated CSR generation, locked or unlocked; it converges after one apply unless the setting cannot take effect (for example, a parent folder locks service generation), in which case the change keeps being reported. An omitted `serviceGenerated` is still not compared.
* Fixed `venafi_certificate` crashing with a `TypeError` on a local or service-generated CSR when `privatekey_path` was omitted. The generated key is now written next to the certificate, at `cert_path` with its extension replaced by `.key` (the documented "placed near certificate with key suffix" behavior), with mode `0600`. The key path is derived only when the module generates the key: a user-provided CSR (`csr_origin: provided`, or an existing `csr_path` file) keeps the 1.3.1 behavior (no key file is read or written; the key stays with your CSR), and with `use_pkcs12_format: true` the key is stored only inside the PKCS#12 file. Upgrade notes: a certificate that 1.3.1 enrolled from a local/service CSR without `privatekey_path` has no key file (1.3.1 discarded the generated key), so the first 1.4.0 run re-enrolls it once and writes the key; with `renew: false` such a certificate reports `changed` on every run, without re-enrolling, until a run with `renew: true` (the default) re-enrolls it. An unrelated private key already stored at the derived path is overwritten when the certificate is enrolled; set `privatekey_path` to keep it.
* `venafi_certificate` now fails before enrolling when the private key path (explicit or derived) is the same file as `cert_path` or `chain_path` (for example `cert_path: server.key` with `privatekey_path` omitted, or `chain_path` equal to the derived `.key` path), also when the paths name that file differently (`./`, `..` or a symlink). Writing the key would overwrite the certificate or chain, so every later run failed to load the certificate (or the chain file silently held the private key). Set `privatekey_path` to a separate file.
* Fixed `venafi_certificate` crashing with a raw `TypeError`/`ValueError` traceback when the private key file is encrypted and `privatekey_passphrase` is missing or wrong, or when the file is not a PEM private key. The task now fails with `Failed to load private key file ...` and leaves the key file untouched.
* Fixed `venafi_certificate` re-enrolling the certificate and failing with `Insufficient file permissions` on every run when `mode` grants group or other access (for example `mode: "0644"`). `mode` was also applied to the private key and PKCS#12 file, leaving the key readable by other users, and the module's own permission check then rejected it. The private key and PKCS#12 file now get `mode` without group/other permissions (`0644` and `0640` become `0600`; a stricter mode such as `0400` is kept). The certificate and chain still get `mode` as given, and the key still defaults to `0600` when `mode` is not set.
* Fixed the `ssh_ca` role failing on every run with `ssh_ca_remote_execution: true`: the remote path read the principals from an undefined variable (`ca_out` instead of the registered `ssh_ca_out`).
* The `certificate`, `policy`, `ssh_ca`, and `ssh_certificate` roles no longer print the contents of `credentials_file` (tokens, access tokens, NGTS client secrets) when a playbook runs with `-v` or higher: the task that loads the file now sets `no_log: true`. As a result, if the file is missing or is not valid YAML, the error detail is censored; the task name still shows the path that was used.

##### 1.3.1
* Bumped the `vcert` dependency to `vcert>=0.21.1` in `requirements.in` and regenerated the hash-pinned `requirements.txt` lockfile (`vcert==0.21.1`). `vcert` 0.21.1 fixes service-generated CSR (`csr_origin: service`) enrollment on CyberArk Certificate Manager, Self-Hosted (TPP): the requested key specification (key type and size, e.g. RSA 4096) is now sent on the enrollment request, so TPP no longer silently falls back to the policy-folder default key size. This resolves the `Private key file does not contain a valid private key` failure in the `venafi_certificate` module that occurred when `privatekey_size` did not match the policy default (surfaced after upgrading to TPP 25.1+/25.3). Delivered entirely through the updated `vcert` SDK — no collection code changes.

##### 1.3.0
* Added the `venafi_certificate_revoke` module to revoke a certificate on CyberArk Certificate Manager, Self-Hosted (TPP), SaaS, and NGTS (Strata Cloud Manager). Self-Hosted (TPP) revokes by certificate DN (`certificate_dn`) or SHA-1 `thumbprint` and honors retire/`no_retire`; SaaS and NGTS revoke by SHA-1 `thumbprint` (the DN and the `ca-compromise` reason are not supported, and `no_retire` is ignored). The reason vocabulary matches the Go `vcert revoke` command (`none`, `key-compromise`, `ca-compromise`, `affiliation-changed`, `superseded`, `cessation-of-operation`). Revocation is imperative: the module always attempts to revoke and the inherited `state` option is accepted but ignored.
* Bumped the `vcert` dependency to `vcert>=0.21.0` in `requirements.in` and regenerated the hash-pinned `requirements.txt` lockfile. SaaS and NGTS certificate revocation is only available in `vcert` 0.21.0; Self-Hosted (TPP) revocation also works on earlier releases.

##### 1.2.0
* Bumped the `vcert` dependency to `vcert>=0.20.0` in `requirements.in` and regenerated the hash-pinned `requirements.txt` lockfile (`vcert==0.20.0`). `vcert` 0.20.0 adds NGTS policy management on top of the NGTS support and security fixes introduced in 0.19.0 — sensitive data redacted from debug logs (CWE-532), safe YAML loading in the policy parser (CWE-502), and TLS verification enabled by default with a warning when disabled (CWE-295). These are backward compatible: the collection already passes `verify` only when a `trust_bundle` is supplied (otherwise `requests`' default of verified TLS applies) and uses plain-data policy specs.
* Added support for NGTS (Strata Cloud Manager) certificate enrollment and renewal in the `venafi_certificate` module and `certificate` role. NGTS is selected by supplying the OAuth2 service-account credentials (`client_id`, `client_secret`, and `tsg_id` or `scope`); `url` and `token_url` are optional and default to the Palo Alto production endpoints.
* Added support for NGTS (Strata Cloud Manager) policy management (`get_policy`/`set_policy`) in the `venafi_policy` module and `policy` role. NGTS zones are the issuing-template (CIT) alias only — there is no Application or owner layer, so the policy specification's `users` and `owners` are ignored and read back empty (parity with the Go reference implementation).
* NGTS supports certificate and policy operations. The `venafi_ssh_certificate` and `venafi_ssh_ca` modules fail fast with a clear message when NGTS credentials are supplied.
